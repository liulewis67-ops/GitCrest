# 升级失败后的数据库恢复

GitCrest 的本地数据库（仓库列表、任务历史、搁置区、操作恢复记录等）在应用升级时可能需要迁移到新的结构。迁移不可逆，因此有两道保护。

## 升级前的自动备份

打开一个**已有的、较旧版本**的数据库时，GitCrest 在第一次写入之前，把它另存为同目录的：

```
<数据库文件名>.before-schema-<新版本号>.bak
```

例如 `gitcrest.sqlite.before-schema-23.bak`。要点：

- 每个目标版本只做一次，已存在的备份**不会被覆盖**；全新安装的数据库不会备份。
- 备份是 SQLite 一致快照，内容是升级**之前**的状态。
- 备份是尽力而为：复制失败不会阻止应用启动。
- 备份**不会自动删除**，也**没有**自动恢复入口。需要时按下面的步骤手工恢复。

## 旧版本遇到新版本的数据库

如果用一个更旧的 GitCrest 打开已被新版本升级过的数据库，旧版本会拒绝启动并说明：该数据库由更新版本创建、给出两边的版本号，并提示更新 GitCrest 或恢复升级前的备份。它在这之前**不会改动**该数据库文件。

## 手工恢复

数据库默认位于应用的用户数据目录下，文件名为 `gitcrest.sqlite`（Electron 的 `userData`；Windows 上通常在 `%APPDATA%` 下以应用命名的文件夹里）。如果设置了环境变量 `GITCREST_DATABASE_PATH`，则以它为准。

1. **完全退出 GitCrest**（含可能仍在后台运行的进程），确保数据库没有被占用。
2. 把当前的 `gitcrest.sqlite` 连同同目录下可能存在的 `gitcrest.sqlite-wal`、`gitcrest.sqlite-shm` 一起**移到别处留存**，不要删除。
3. 把需要的备份文件复制为 `gitcrest.sqlite`（去掉 `.before-schema-N.bak` 后缀）。
4. 用与该备份兼容的 GitCrest 版本启动。

## 恢复前要知道的

- 备份只包含升级之前的数据。升级之后新增的内容（新的仓库记录、任务、搁置、操作等）不在其中，恢复后会丢失；所以第 2 步要留存现有文件。
- 搁置区和操作恢复记录里保存的修改副本也在数据库里；恢复到升级前的备份，就回到备份时刻保存了哪些副本。
- 如果有尚未完成的持久操作（需要恢复），请先在新版本里处理完再决定是否回退，否则回退会让这些操作的恢复证据一并回到旧状态。
