# GitCrest 后端开发规范

本文规定 Rust 后端的目录结构、模块依赖、API 契约和可靠性要求，适用于 `crates/gitcrest-core`。目录中的注释只描述职责。

## 1. 适用范围与约束等级

GitCrest 后端是运行在用户计算机上的 Rust sidecar，由 Electron 主进程管理，通过本地 HTTP 和 WebSocket 提供能力。可扩展性包括新增业务能力、替换 Git/存储适配器，以及在多仓库、大仓库场景下控制资源开销。

高可用要求覆盖故障隔离、及时发现异常、受控重启、任务恢复和数据保护。单机 sidecar 存在进程重启窗口；主机宕机、磁盘损坏及外部服务故障有各自的恢复边界，不能通过目录分层宣称消除这些风险。

- **必须 / 禁止**：代码评审和发布验收的硬性要求。
- **应**：默认采用；偏离时须在变更说明中记录原因、影响和替代保障。
- **可**：按业务复杂度选择，不作为统一强制条件。

相关依据：

- [领域术语](../CONTEXT.md)：Repository、RepoId、Git directory 和 worktree 的定义。
- [Git 引擎架构](12-git-engine-architecture.md)：产品能力及业务流程。
- [HTTP API 契约](api/v1.yaml)、[事件协议](api/events-v1.md)：路径、字段、状态码、版本和事件的对外约定。
- [实施与验收规则](13-implementation-plan.md)：开发阶段和验收证据。

本文定义工程规则。涉及新增端点、错误码、字段或事件时，必须先在同一变更中同步契约；目录或示意图不能替代 OpenAPI，也不能直接改变已有客户端行为。

## 2. 核心原则

1. **薄入口**：`main.rs` 只调用启动入口并处理最终退出。配置、依赖构造、路由、业务逻辑各有归属。
2. **语义聚合**：一组相近语义的 API 归属一个业务模块；禁止把所有 handler 堆入同一个文件。
3. **职责分层**：协议解析、用例编排、领域规则和外部系统适配分别负责自身边界。
4. **单一模型归属**：领域模型在 `domain/` 定义一次；API DTO、数据库行和领域模型分别转换，不能各自定义一套冲突的业务规则。
5. **显式依赖**：依赖从启动层注入。模块不能通过全局变量、其他模块的内部文件或隐式服务定位器取得依赖。
6. **资源有界**：请求、队列、并发、缓存、日志、事件和后台任务都必须有容量、时间及清理规则。
7. **失败可恢复**：错误、取消、超时和中断必须保留可判断的状态；不能把“请求已返回”视为“副作用已停止”。
8. **数据保护优先**：未知执行结果先核对，不自动重复危险写操作；恢复不得覆盖用户无关修改。
9. **可观测、可验收**：每条可靠性规则必须能通过日志、指标或故障场景验证。

`main.rs` 的启动路径固定为：入口 → `bootstrap::run()` → 配置校验 → 依赖组装 → 恢复检查 → 服务监听与就绪通知。stdout 专用于 Electron 约定的进程协议；普通日志输出到 stderr 或受控日志文件。

## 4. 依赖与可扩展性

### 4.1 依赖方向

```text
bootstrap                         组装所有具体实现
  ├─ API/feature handlers         解析协议，调用 feature service
  ├─ feature services             编排用例，依赖 domain + ports
  └─ execution/git/storage/...    实现 ports，依赖 domain + ports

ports → domain
domain → Rust 标准库与确有必要的纯数据依赖
```

- `domain/` 必须独立于 axum、HTTP 状态码、数据库连接、Git 子进程和 Electron；这里不定义 API 序列化策略。
- `ports/` 的签名只使用领域类型或中立的 Rust 类型，不能泄露 `Json<T>`、数据库行、WebSocket 或具体引擎句柄。
- `features/*/service.rs` 不直接引用 `git/`、`storage/` 的具体实现。只有具备外部副作用、替换需要或隔离测试价值的能力才定义 trait；纯业务函数直接调用。
- feature 不导入其他 feature 的 handler、DTO 或私有实现。跨能力编排通过 ports 和领域组件完成；禁止循环依赖。
- `bootstrap.rs` 注入具体实现并注册类型化任务执行器。`execution/` 管调度和生命周期，业务 feature 的执行器决定操作步骤，Git 适配器执行底层动作。
- `features/tasks/` 负责任务 API；`execution/` 负责执行机制；任务状态机只在 `domain/task.rs` 定义。
- 引擎替换通过能力接口完成；不同 Git 引擎必须通过相同契约场景。发生未知写入结果后，禁止自动切换引擎再执行一次。
- 模块默认私有，crate 内共享使用最小必要的 `pub(crate)`；`lib.rs` 只导出构造器和真正需要的稳定类型。暂时可在单 crate 内保持边界；提取新 crate 必须有独立复用、构建或所有权理由。

### 4.2 模型与状态

| 类型                              | 唯一归属                  | 约束                            |
| --------------------------------- | ------------------------- | ------------------------------- |
| Repository、Task、Diff 等领域模型 | `domain/`               | 字段不变量由构造器和方法维护    |
| 请求、响应和 API 分页 DTO         | 对应 feature 的`dto.rs` | 由契约决定字段、null 和枚举语义 |
| 数据库行与序列化存储版本          | `storage/`              | 显式转换为领域对象              |
| API 事件 envelope                 | `events/envelope.rs`    | 与领域事件分开，按协议版本映射  |
| 引擎原始对象与解析结果            | `git/`                  | 不直接跨 API 或持久化边界传播   |

`AppState` 保存可克隆的服务句柄和不可变配置。handler 取得最小所需状态，service 接收明确依赖，禁止把整个 `AppState` 传遍业务层。RepoId、TaskId、资源版本等使用不同类型避免混用；路径使用 `Path/PathBuf`，不得通过字符串拼接推断资源身份。

## 5. API 分组与契约

### 5.1 路由归属

| 语义                          | feature                                | 路由组织规则                                     |
| ----------------------------- | -------------------------------------- | ------------------------------------------------ |
| 存活、引擎版本和运行状态      | `system`                             | `/health`、`/api/version` 按契约保留各自边界 |
| 仓库生命周期、最近仓库与收藏  | `repositories`                       | 仓库集合和单个仓库资源                           |
| 工作区快照与刷新              | `status`                             | 仓库下的状态资源                                 |
| 暂存与取消暂存                | `staging`                            | 仓库下的暂存操作                                 |
| 分支、标签、远程配置与同步    | `branches` / `tags` / `remotes`  | 三组 API 分开维护                                |
| 创建提交、查询历史、查询 Diff | `commits` / `history` / `diff`   | 按写用例和查询语义分组                           |
| 合并、变基和冲突处理          | `workflows`                          | 同一工作流的预检、执行、继续和中止               |
| Shelve、任务、设置            | `shelves` / `tasks` / `settings` | 各自独立的资源组                                 |
| WebSocket                     | `events`                             | `/api/v1/events`，与 HTTP 使用相同认证边界     |

每组提供一个 router 构造函数，handler 为模块内部实现。顶层 router 只组合子路由、统一中间件和 fallback；共享 `/repositories/{repoId}` 前缀并不意味着所有子资源必须写进仓库路由文件。

完整路径由路由注册约定唯一确定：版本前缀由顶层提供，资源前缀和参数由子 router 声明，禁止重复拼接。API 测试必须覆盖集合根路径、参数路径、尾斜杠、404 和 405，不能依赖框架默认行为恰好符合契约。

### 5.2 请求与响应

- handler 只做解析、边界校验、权限上下文传递、调用用例和 DTO 转换。业务约束在应用/领域层再次保证，避免后台任务入口绕过。
- JSON、路径、query 的 extractor 拒绝响应以及 413、超时、过载、404、405 都必须走约定的错误 envelope。
- 成功响应不强制增加全局 `data` 包装；以具体契约为准。Rust 字段使用 `snake_case`，JSON 按契约映射 `camelCase`。
- 400 用于输入错误，401/403 区分未认证/无权限，409 用于状态冲突，412 用于过期资源，413 用于超限，429/503 区分调用方限流与服务暂不可用。错误码、重试提示和响应头必须同步进 OpenAPI。
- API 版本不支持保持 406；错误中不得回传 token、credential 或原始敏感 stderr。
- 长任务提交在任务与必要去重记录持久化后返回 taskId；采用 202 接受语义的端点须在契约中明示。已受理任务可通过查询恢复，不能依赖提交响应或 WS 消息必达。
- 写操作鉴权按能力和副作用定义，不能仅用 HTTP method 推断。只读 POST 查询与改变状态的操作须有明确分类；任务取消、继续、设置更新也必须检查权限。
- 危险操作预检生成有期限的确认票据，绑定目标、操作参数、权限、资源版本和影响范围；执行前重新核对，不能用一个裸 `confirmed: true` 代替。

### 5.3 版本与兼容性

修改 API 时，必须同步 `doc/api/v1.yaml`、Rust DTO、前端类型和消费者验证。使用 `pnpm api:types` 生成 TypeScript 类型，禁止手改生成文件。

破坏性变更包括字段删除/改名/改类型、默认行为改变、状态码改变、严格消费者无法处理的新枚举或字段。不能假设“只加字段”一定兼容；特别要检查 `additionalProperties: false`、穷举分支和校验器。不能兼容时使用新的 API/事件主版本，并明确迁移窗口。

集合查询必须明确排序、分页大小和最大值。大历史使用绑定查询条件及快照版本的游标；游标失效时要求刷新，不能在变化的数据上悄悄重复或漏项。大型 Diff 必须声明截断、按块加载或流式协议，不能无界构造 JSON。

## 6. 并发、Git 写入与一致性

### 6.1 资源锁

- 同一工作树的写操作串行执行。共享 common Git directory 的 worktree 还需要共享资源锁；保守默认按 common Git directory 串行化写入，只有证明资源互不冲突后才细化。
- RepoId 表示一个工作树，不能用它代替所有写锁的身份。资源身份由仓库解析器提供，不对所有平台路径简单转小写，也不手拼 `.git` 目录。
- 多资源操作必须按稳定顺序获取锁，明确等待期限；进入可执行状态再占用 worker，避免一个繁忙仓库耗尽所有执行槽位。
- **内存数据锁**只保护短小读写，不能跨 Git/数据库 I/O 持有；**操作互斥许可**必须覆盖预检、实际副作用、结果核对和关键快照失效，允许跨这些必要的 await 持有。两者不能混淆。
- 进程内锁无法约束用户终端和其他 Git 客户端。必须保留 Git 原生锁和引用前置条件；不能自动删除未知归属的 `index.lock` 或将它直接判为死锁。
- 关联仓库和 submodule 操作必须列出涉及的资源；无法获得完整安全执行条件时拒绝或进入等待，不能部分执行后声称整体成功。

Linked worktree 具有独立的 HEAD/index，并共享部分引用等仓库资源；上述锁规则据此限定跨 worktree 的并发。[Git worktree 官方说明](https://git-scm.com/docs/git-worktree)

### 6.2 快照与外部变更

缓存用于查询加速，真实 Git 状态决定写入条件。快照必须有版本和新鲜度信息；关键写入在获得操作许可后重新读取并检查 HEAD、目标 ref、index 和相关文件内容，过期 patch 必须拒绝。

读取必须明确一致性需求：不可变 Git 对象可并行读取；跨 index/工作树的组合快照须协调写入或检测读取期间的变化并重读。单靠进程内版本号不能检测外部 Git 操作，也不能消除文件系统竞态；必须结合 Git 自身的原子操作、预期旧值和操作前后核对。

文件监听必须去抖、合并并保留刷新期间新到的 dirty scope。监听溢出、断连或异常时标记全量失效，使用有界全量刷新或轮询补偿。Git 写入结束后主动失效相关快照，不只等待 watcher。快照发布使用版本比较，禁止旧刷新结果覆盖新版本；缓存按仓库和字节数限制容量。

## 7. 任务、幂等与恢复

### 7.1 执行模型

`execution/` 必须维护有界队列、全局并发和按仓库公平调度；队列满时拒绝受理，不能先返回 taskId 再丢弃任务。涉及副作用的 Git 操作必须经过统一执行协调器，禁止 handler 或其他后台协程绕过锁、审计和恢复规则。

任务描述使用类型化操作与版本化参数，不能接收任意 shell 字符串。执行器明确锁资源、权限、超时、取消能力、影响范围、检查点及恢复方法。clone 等没有已注册 RepoId 的操作仍须使用规范化目标目录作为资源身份。

任务至少保存 taskId、操作类型/版本、目标、输入摘要、状态、阶段、结果或错误、创建/更新时间、去重键与恢复信息。敏感凭据只在执行时从凭据服务获得，不进入任务持久化数据。

### 7.2 状态与取消

对外 TaskStatus 使用契约定义的 `queued`、`running`、`waitingForInput`、`succeeded`、`failed`、`cancelled`。领域内部的取消请求、检查点和恢复标记与这些状态明确映射；新增状态不能绕过契约版本管理。

| 场景                       | 要求                                                         |
| -------------------------- | ------------------------------------------------------------ |
| queued → running          | 唯一执行者成功认领，前置条件有效，副作用前保存必要检查点     |
| running → waitingForInput | 冲突/凭据等需要交互，记录可继续条件，不长期占用 worker       |
| waitingForInput → running | 重新校验权限、目标版本并重新取得操作许可                     |
| running → succeeded       | 已核对实际结果并保存结果；缓存刷新失败单独标为需要重同步     |
| 取消请求                   | 先传递取消意图；安全停止并核对副作用后才能决定终态           |
| 意外中断                   | 保留不确定状态及恢复标记，核对后映射到失败、等待处理或已成功 |

终态不得被延迟的进度消息回写成 running。重试创建关联的新尝试或按明确规则继续检查点，不能直接把终态重置。

超时只表示超过等待期限。HTTP 断开不自动取消已受理任务；终止 Future 不代表 Git 子进程或阻塞线程已经停止。必须协作取消并回收子进程树，确认执行者退出后才能释放写入许可。已完成的操作与取消竞争时以核对结果为准；`cancelled` 不承诺回滚，必须说明保留的部分结果和恢复路径。

Tokio 的已启动 `spawn_blocking` 任务不能通过 abort 停止，因此 CPU/阻塞工作还必须有并发额度、安全停止点或进程隔离方案。[Tokio spawn_blocking 文档](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html)

### 7.3 幂等与重试

- 会产生重复副作用的提交端点必须约定幂等键；作用域至少覆盖本地应用数据身份、操作类型和目标。同一键与不同输入摘要冲突时拒绝，同一键同一输入返回原 taskId/结果。
- 幂等记录和任务受理必须在同一数据库事务中提交，并由唯一约束处理并发重复请求；不能用内存 map 作为重启后的唯一依据。
- 每次请求仍要鉴权。幂等命名空间不能仅依赖会随 sidecar 重启变化的 token。
- 保留期必须覆盖客户端重试窗口；未结束或待核对任务的去重记录不得清理。窗口到期后客户端不得盲目重发，应先核对原任务/目标。
- 仅对明确可重试的瞬时错误采用有上限的指数退避和抖动，并计入统一 deadline。认证失败、输入错误、前置条件失败不自动重试。
- 对 commit、push、reset 等未知结果的写入，必须核对实际状态；无法证明结果时进入需人工处理的恢复路径，禁止自动重放。幂等键不等于跨数据库和 Git 的“恰好执行一次”。

### 7.4 崩溃恢复

数据库事务不能与 Git/文件系统副作用形成一个原子事务。必须处理“Git 已成功但数据库结果未保存”的窗口：

1. 副作用前持久化操作意图、目标前置条件、执行阶段及必要备份引用。
2. 重启后识别未结束任务，确认旧执行者和子进程树已退出；有疑义时阻止相关资源的新写入。
3. 按操作核对实际 ref、index、工作树、远端或目标目录，判断已完成、未开始、部分完成或无法确定。
4. 已完成则补记结果；只对被证明安全的步骤继续；部分完成或不确定则提供继续、中止或人工恢复入口。
5. 重建快照并要求客户端重新同步。备份只保护明确覆盖的内容，不能把备份 ref 当作未提交工作区内容的完整备份。

## 8. 本地服务可用性与生命周期

### 8.1 监督与就绪

Electron 主进程是 sidecar 的唯一监督者，负责启动超时、进程退出和无响应检测。Rust 管理自身后台任务；renderer 不自行启动第二份服务。每个应用数据目录必须只有一个受协调的写入实例。

存活、就绪和降级状态必须分开：

- `/health` 按契约返回最小存活信息，不执行 Git、磁盘扫描或外部网络检查，也不泄露会话数据。
- 就绪状态汇总依赖初始化、恢复检查和关键 worker 的状态；详细状态只能通过受保护的协议提供，不能修改公开健康检查来泄露诊断。
- 降级应描述具体受影响能力。一个失效仓库或 remote 不能把所有仓库判为不可用。
- 监听成功且完成启动安全检查后才输出 ready 消息。恢复过程中可显式进入只读降级，但必须在受保护状态中说明写入能力受限。

监督者对非预期退出或持续无响应采用有抖动的指数退避；默认自动恢复预算为 **10 分钟内最多 5 次重启，退避上限 30 秒**。达到预算后保留诊断并提示用户处理，禁止无限重启。认证配置错误、数据库迁移失败等确定性错误不得靠反复重启掩盖。

重启后重新建立端口和会话凭据，旧连接失效，客户端重新获取连接信息与快照。只能在确认旧进程和相关写入子进程已停止后建立新的写入执行者。

### 8.2 优雅退出

退出流程必须有总期限，默认 10 秒，可通过校验后的配置调整：

1. 标记 draining，停止接受新写任务并停止周期调度。
2. 通知 watcher、WS、后台 worker 和任务执行器停止或进入安全检查点。
3. 等待短请求结束；对长任务协作取消，记录需要恢复的状态。
4. 回收子进程树，关闭连接，完成必要的持久化和日志刷新。
5. 超过期限时由监督者采取受控终止；下次启动按中断恢复流程核对，不把强制退出当作已回滚。

关闭过程分为发出通知、传播取消和等待结束；所有后台任务必须有所属监督者及可等待的句柄，不能随意 detach 后失去管理。[Tokio 优雅退出说明](https://tokio.rs/tokio/topics/shutdown)

### 8.3 故障隔离和降级

| 故障                     | 服务行为                            | 恢复条件                    |
| ------------------------ | ----------------------------------- | --------------------------- |
| 某个仓库失效或权限变化   | 标记该仓库异常，拒绝对应操作        | 用户修复路径/权限后重新校验 |
| 网络或凭据失败           | 结束/暂停对应远程任务，保持本地查询 | 明确重试或补充凭据          |
| watcher 异常             | 标记快照过期，启用有界轮询/全量刷新 | 重建监听并完成重同步        |
| 数据库只读、满盘或不可写 | 拒绝依赖持久化的受理，保留安全读取  | 存储可用并核对任务日志      |
| 缓存损坏                 | 丢弃可重建缓存，回源读取            | 有界重建成功                |
| 单个执行任务 panic       | 记录异常，隔离目标资源并核对副作用  | 状态可证明安全后解除隔离    |
| 关键调度器或核心状态失效 | 停止写入准入并受控退出              | 监督者重启并完成恢复        |

降级不能伪装成功，不能静默丢失收藏、设置或任务记录。禁止“数据库打不开就删掉重建”；缓存和用户持久化数据必须有明确区分。无法证明全局状态安全的 panic 必须交由进程恢复处理。

## 9. 资源上限与性能

所有上限在 `config.rs` 集中定义默认值、单位、合法范围和覆盖方式。以下为工程默认预算，修改必须提供对应负载证据，不表示实测结果。

| 资源                 | 默认预算                      | 达限行为                               |
| -------------------- | ----------------------------- | -------------------------------------- |
| 普通 JSON 请求       | 1 MiB                         | 413；patch/大数据端点单独声明上限      |
| 分页                 | 默认 100 条，最大 500 条      | 非法大小拒绝，不偷偷全量返回           |
| 普通查询总时间       | 10 秒，含等待                 | 取消可安全取消的读取并返回统一超时错误 |
| 已受理长任务等待队列 | 全局 128，每个资源组 16       | 拒绝新增受理；已持久化任务不丢弃       |
| 活跃 Git 子进程      | 全局 4，同一写资源组 1        | 公平等待；不耗尽普通查询资源           |
| CPU 密集工作         | 最多 max(1, 可用逻辑核数 / 2) | 有界等待，不无限提交阻塞任务           |
| WS 连接              | 每个会话 16                   | 拒绝多余连接                           |
| 每连接待发送事件     | 256 条且不超过 1 MiB          | 标记需重同步或关闭慢连接               |
| 快照和 Diff 缓存     | 全局 128 MiB                  | 按仓库配额及 LRU 淘汰                  |
| 任务日志             | 每任务 10 MiB，全局 100 MiB   | 轮转并显式标记截断                     |

长任务按操作定义排队期限、执行期限、网络无进度期限及暂停交互期限；不得套用普通 HTTP 超时，也不得默认永久等待。等待用户输入时释放 worker 和长期锁，持久化工作流占用状态并拒绝不兼容的新写入；继续时重新取得操作许可并预检。

进程内超时和耗时统计使用单调时钟；事件及持久化记录使用有单位的 UTC 时间。重启后根据持久化阶段和过期策略重新建立 deadline，不能序列化单调时钟值，也不能让系统时间跳变悄悄扩大重试窗口。配置不合法必须明确失败，不能静默回退到无界限制。

准入限制必须发生在耗时解析和入队之前；队列、信号量等待者、输出缓冲区和后台刷新请求都必须有界。队列满时的 429/503、重试提示与错误码按 API 契约实现。

子进程 stdout/stderr 必须并发排空，按协议流式解析或限制保留体积。达到日志上限后仍需排空或安全终止，禁止因停止读取导致子进程卡死。凭据交互和长任务应保留取消通道，健康检查不能被工作队列饱和拖死。

## 10. 事件和客户端重同步

WebSocket 事件是内存通知；持久化任务查询与真实仓库快照提供恢复依据。`eventId` 只在 sidecar 会话内有意义，不能用作重启后的恢复游标。

- 使用受控 Electron 传输在 upgrade 中附加 Authorization；token 不放 URL、子协议或消息体。子协议和不兼容版本关闭码遵循事件协议。
- 首次连接、重连、事件缺口、未知事件或慢消费者溢出后，必须重新获取仓库列表及所选仓库相关完整快照。
- 快照抓取期间仍可能发生变化。客户端必须缓冲失效标记，收到期间的相关通知则再刷新，直到获得可接受版本；不能简单清空事件后宣布同步完成。
- 单连接的事件投递必须保证约定顺序。若按仓库过滤，事件编号及缺口检测语义必须在协议中明确，不能把正常过滤误判为丢包。
- 高频进度和失效通知可合并。任务终态先持久化再发通知；漏掉终态通知时客户端仍能查询恢复。
- 连接必须有心跳/空闲检测、有界发送缓冲和断开清理。慢消费者不得阻塞业务提交；无法可靠发送重同步通知时直接断开，让重连流程触发完整刷新。
- 默认不引入持久化消息队列或 outbox；只有业务明确要求通知持久交付时，才新增相应契约和存储机制。

## 11. 存储、升级与备份

- SQLite 数据库存放在应用专属本地数据目录。连接数、事务时间和 busy 等待有上限；SQL 参数化，状态变更和幂等认领使用事务与唯一约束。
- WAL 支持读写并行，但同一时刻仍只有一个 writer，且不能假定可用于网络文件系统。短事务之外必须监测 checkpoint 与 WAL 体积，避免长读事务阻止回收。[SQLite WAL 文档](https://sqlite.org/wal.html)
- 接受任务、用户设置、收藏和恢复日志按持久化数据处理，WAL 模式下默认使用 `synchronous=FULL`；初始化时必须核对实际 journal/synchronous 配置，各连接启用所需外键约束。可重建缓存才能采用较弱的持久性策略。不能在不记录取舍的情况下为了性能降低保护。
- 任务受理记录先提交再返回；写入结果不能在事务失败后仍报告已持久化。进程崩溃后的恢复和断电后的恢复须分别验证，硬件/文件系统仍构成耐久性的边界。
- `migrations/` 使用唯一递增版本，发布后的迁移不可改写。迁移前检查兼容版本并备份；可事务化的变更使用事务，其他变更必须有检查点与明确恢复方法。
- 新增 schema 优先采用可兼容的扩展；删除字段或改变语义须安排迁移窗口。旧版本遇到不支持的 schema 必须拒绝写入，不能强行降级打开。
- 在线备份使用 SQLite 一致性备份接口等安全方式；禁止仅复制运行中的主数据库文件。必须实际验证备份可打开、可恢复，并按容量和保留期清理。[SQLite Backup API](https://sqlite.org/backup.html)
- Shelve、恢复 patch 等额外文件与数据库不能假设原子提交：使用临时文件、完整性校验、原子替换和可核对的记录顺序；中断后识别缺失/孤立文件，不删除无法确认归属的用户内容。

## 12. 安全、错误与可观测性

### 12.1 本地信任边界

只监听 `127.0.0.1` 和分配的随机端口，非法监听配置必须拒绝启动。所有业务 API 和 WS 都需要认证；CORS 使用精确允许列表，不能把 CORS 视为身份验证。

初次打开、初始化、clone 接收用户明确选择的目标；后续仓库操作使用 RepoId。仓库内相对路径须检查越界、符号链接及平台路径语义，允许读取指向仓库外的链接内容必须是显式能力，不能默认跟随写入。

Git 执行采用固定子命令与独立 argv，必要时使用 `--` 分隔路径参数；还须校验 option、ref 和协议，防止“参数未经过 shell”却被 Git 解释为选项。hooks、过滤器、凭据 helper 和外部 diff 具有执行代码能力，必须纳入可信仓库/受控执行策略，不能把只读 API 自动等同于无副作用执行。

凭据通过系统 keyring 或受控交互获取，不存进任务描述、日志、URL query、普通配置及前端持久化缓存。

### 12.2 错误与诊断

领域错误表达可采取的动作，底层错误保留 source 链；API 边界统一映射并脱敏。禁止把所有异常合并为“仓库不存在”，也禁止通过用户错误触发 panic。生产流程不使用 `unwrap()` 处理正常失败；可证明的不变量才使用带理由的 `expect()`。

每个请求和任务具有独立关联标识。结构化日志包含操作名、阶段、requestId、taskId、repoId、队列等待、执行耗时、结果类别和重试次数；认证信息、敏感路径和仓库内容必须脱敏。

指标至少覆盖：请求 p50/p95/p99、错误分类、队列深度/等待、执行槽占用、锁等待、取消耗时、任务中断/恢复、WS 丢失/重同步、数据库 busy、缓存体积和 sidecar 重启。指标标签使用操作类型等有限集合，不能把 taskId、路径等高基数字段作为标签。

诊断导出应有大小和保留期限，默认不含源码、Diff 正文和凭据。超时、容量不足、依赖不可用与程序缺陷必须能从日志区分。

## 13. 可用性目标与验收

### 13.1 衡量口径

以下为发布验收目标，不构成已经达到的运行结论。每次验收必须记录操作系统、硬件、Git 版本、仓库规模、后台负载和测量脚本。

| 目标           | 验收口径                                                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| API 可用性     | 在声明支持的负载内，24 小时持续运行期间对轻量本地查询每秒探测一次，1 秒内取得有效响应的比例 ≥ 99.9%；非预期重启窗口计入失败         |
| 故障后恢复时间 | 单次可恢复 sidecar 崩溃，在磁盘正常、无迁移、无人工恢复阻塞时，从进程退出到安全就绪并能读取本地状态 ≤ 10 秒；大仓库全量刷新单独计时 |
| 数据恢复       | 在进程崩溃场景中，已经确认持久化的用户设置、收藏和任务受理记录不丢失；未知 Git 副作用可追踪、可核对                                  |
| 请求隔离       | 长 Git 任务、慢 WS、一个故障仓库及队列饱和时，健康检查和其他仓库的轻量查询仍在上述探测阈值内响应                                     |
| 资源稳定       | 在规定缓存/日志预算内完成 24 小时压力运行，连接、任务和仓库关闭后无持续增长的句柄、协程与内存占用                                    |
| 正常退出       | 10 秒默认退出预算内停止服务，无法完成的操作具有可核对的恢复记录，无未管理的写入子进程                                                |

主机休眠、用户主动关闭应用和测试计划中的维护时间不计入上述 API 探测分母；远程服务与断电故障另外统计。RPO 0 的表述只针对已确认持久化的应用记录和明确验证的故障模型，不能推广成所有 Git/文件系统/远端写入的零损失保证。

### 13.2 测试分层

- 单元测试：领域状态机、权限、前置条件、DTO 映射和队列策略；靠近所属模块，不镜像内部实现。
- 适配器测试：临时仓库、linked worktree、本地 bare remote、临时数据库和模拟凭据；不得操作开发者真实仓库。
- API 契约测试：完整 router 的路径、HTTP method、版本、鉴权、CORS、extractor 拒绝、错误封装和输入上限。
- 生命周期/恢复测试：独立子进程中注入 panic、强制退出、超时和存储错误，核对仓库副作用与恢复状态。
- 跨平台场景：Windows/macOS/Linux 的路径、空格与非 ASCII 名称、权限、符号链接、进程树和 Git 行尾差异。

### 13.3 必须覆盖的故障场景

| 故障注入                                               | 必须验证                                           |
| ------------------------------------------------------ | -------------------------------------------------- |
| 受理完成但提交响应丢失                                 | 同键重试返回原 taskId，不重复副作用                |
| Git 已成功、结果落库前退出                             | 重启核对实际结果，不盲目重新执行                   |
| 同 worktree 并发写与共享 common 目录的不同 worktree 写 | 冲突资源串行，独立资源仍可前进                     |
| 外部终端修改 HEAD、index 或目标文件                    | 前置条件失效被发现，未选改动不被覆盖               |
| 取消与成功同时发生，阻塞调用不响应取消                 | 终态与实际结果一致，未退出执行者不能提前释放写许可 |
| 队列满、输出超大、慢 WS 和 watcher 风暴                | 明确拒绝/截断/重同步，无死锁和无界增长             |
| 数据库 busy、磁盘满、迁移中断、备份恢复                | 不伪报成功，不删除用户数据，可读取诊断和恢复       |
| WS 断线、丢事件、抓取快照期间再次变更                  | 客户端通过快照与失效标记最终收敛                   |
| 多次崩溃与退出期间挂起                                 | 重启预算生效，无双写执行者或孤立子进程             |

## 14. 开发与评审门禁

新增能力按以下顺序完成：

1. 确认 API 语义和唯一 feature 归属，声明模型与依赖方向。
2. 固化契约、权限、错误、分页、幂等和资源预算。
3. 编写领域规则与用例，再实现所需 ports/适配器；由 bootstrap 注入。
4. 对写操作说明锁资源、前置条件、副作用、取消边界和中断恢复步骤。
5. 通过对应层的正常、失败和故障注入场景，更新前端生成类型和文档。
6. 提交验收证据及影响范围，不用目录存在或测试数量代替行为验证。

代码变更应执行项目质量门禁 `pnpm check`，并检查 `cargo clippy --manifest-path crates/gitcrest-core/Cargo.toml --all-targets -- -D warnings`；依赖变更审查维护状态、许可和安全公告。CI 还应检查模块依赖规则与公共出口，防止循环依赖和跨 feature 私有访问。涉及 API 时生成类型后检查差异；涉及迁移、任务或进程管理时补充对应恢复验证。纯文档变更检查链接、示例和规则一致性即可。

评审必须能明确回答：

- 新 API 和业务逻辑放在哪个语义模块，是否绕过 service 或适配器？
- 领域模型是否只有一个定义，依赖是否可以替换并独立验证？
- 每项资源的上限、超时、释放责任和过载响应是什么？
- 失败或重启后，能否判断副作用、避免重复写入并保护用户修改？
- 客户端能否从契约、错误和任务状态中得知下一步动作？
- 验收证据是否覆盖了本次变更的并发、恢复和兼容性风险？

例外必须记录原因、影响范围、替代保障和复审条件；不能以“后续重构”作为长期绕过分层和可靠性规则的依据。
