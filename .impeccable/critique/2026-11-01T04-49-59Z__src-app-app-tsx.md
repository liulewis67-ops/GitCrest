## Design specificity

**Product-specific and coherent.** This is recognizably a Git workbench: staged selection sits next to the commit composer; the selected file owns a large reading pane; history joins graph, refs and commit changes; task outcomes and ahead/behind counts stay close to the work. The neutral palette is appropriate for long code-reading sessions. This would not transfer unchanged to an unrelated dashboard. The main weakness is the amount of configuration surrounding the diff at constrained sizes, rather than generic visual styling.

## Cognitive load

**3 checklist failures, moderate load:** Chunking fails in the diff toolbar and long Settings navigation; Minimal choices fails at the same decision points; Progressive disclosure is partial because rarely adjusted diff preferences remain beside every review. Single focus, grouping, visual hierarchy, one thing at a time and working-memory support pass for the core staged-file-to-commit path: selected file, scope and destination remain in the same workbench. These passes do not excuse the clipped scope summary.

Decision points with more than four visible options:

- Full diff toolbar: eight controls (previous/next change, Structure, layout, whitespace, collapse unchanged, select lines/hunks, open window). These are not all one logical decision; their shared visual weight makes the user sort them first.
- File-list action row: six icon-only controls, grouped weakly by one divider. Tooltips help after exploration.
- Settings: eight visible section choices. Appearance presents up to ten theme cards, with Duplicate on each. This is an optional configuration surface, so the burden is lower than a mandatory commit step.
- History graph and file tree exceed four rows, but are structured data for scanning, not automatically eight-way action overload. Filtering, selection and graph relationships make the list length defensible.

## Emotional journey

Welcome offers a calm start and concrete repository actions. Workspace rewards recognition: current branch, checked staging choices, selected diff and a contained composer make a risky Git operation feel deliberate. The valley is narrow History: graph, changed-files list and wrapped controls compress the actual code; the user must first arrange the workbench. High-stakes confidence is strongest in explicit repository recovery and weakest where “6 staged files” disappears into ellipsis. The completed fetch ends well: a confirmed outcome and time, with raw log collapsed, leave a useful memory of success. Actual commit/push completion was not evaluated.

## Strengths

1. Workspace composition ties review and staged commit scope together without an unrelated dashboard layer. The persistent first-use staging note is short and dismissible; the short-height Chinese image retains a useful file list and composer.
2. Error recovery is a designed surface: readable problem, actionable next step and quiet diagnostic disclosure. The live History failure suppresses stale commit details instead of presenting them as current.
3. Task Center gives completed work a human outcome and relative time, while leaving logs out of the default reading path. The main screen stays quiet between operations.

## Priority issues

### P2 — The palette teaches two incorrect navigation shortcuts

Evidence: live repository palette and 960×700 dark palette screenshot display “Go to Welcome — Ctrl 1” and “Go to Workspace — Ctrl 2,” while lower View commands and Settings display Workspace Ctrl+1 and History Ctrl+2. Live Ctrl+1 opens repository Workspace, not Welcome. `src/app/layouts/CommandPalette.tsx:121` hard-codes those first two hints; `src/app/use-global-shortcuts.ts:150` handles the actual view bindings.

Fix: remove the obsolete top-level hints or give those navigation commands actual distinct bindings from the same preferences source. Never show two different destinations for the same accelerator. This directly affects expert trust and shortcut learning.

### P2 — Commit destination/scope loses the staged count precisely where space is tight

Evidence: 960×700 English Workspace footer reads “Commit to main · 6 s…” beside a wide “Plain message” select. Even the larger initial live capture truncates the tail. The complete accessible text exists, but the count has no dedicated persistent visual slot. `src/features/commits/ui/CommitWorkbench.tsx:175`; `src/styles/globals.css:390`, `:1479`.

Fix: give branch and staged count separate lines or reserve a nonshrinking “6 staged” badge beside the commit action. Move the message template into the composer options or let it yield width first. Keep confirmation-relevant information readable without hover or memorizing checked rows.

### P2 — Narrow History prioritizes diff configuration above the diff itself

Evidence: `.review/a-history-960.png` and the matching dark matrix image: the selected commit occupies the lower portion, the changed-files column consumes about 240px, and eight diff controls wrap into multiple lines. Code begins near y=610 of a 700px window, with each split side roughly 100–200px wide after gutters. The single-line fixture is already cramped. Focus mode is a workaround, but requires another layout decision. `src/features/diff/ui/FileDiffViewer.tsx:119`; `src/styles/globals.css:421`, `:772`; `src/pages/workspace/HistorySplit.tsx:35`.

Fix: at narrow pane widths, keep change navigation and layout visible; place whitespace/collapse/structure/window options under one View menu. Collapse the commit file list when only one file exists, or offer a compact file chooser. Preserve user-selected graph sizing, while choosing an initial split that leaves useful code height.

### P2 — Commit signing options have labels but little decision support

Evidence: three equally weighted options “Amend / Sign-off / Sign” sit at the top of the composer. Sign-off and Sign titles repeat the labels; the latter is a distinct security operation. The amend advisory is good once selected, but there is no equivalent local explanation of the two signing choices. `src/features/commits/ui/CommitWorkbench.tsx:108`; `src/shared/i18n/messages/commits.ts:27`.

Fix: retain the compact row, add concise keyboard-accessible descriptions: Sign-off adds an author attestation trailer; Sign cryptographically signs using configured Git signing. Link the latter to signing status/settings. Do not force a tutorial on experienced users.

## Persona red flags

- **Alex, impatient power user:** incorrect shortcut hints undermine the accelerator path; narrow History needs focus-mode/layout adjustment before serious comparison. Otherwise strong: shortcuts, search, bulk stage, adjustable panes and no forced tour.
- **Sam, keyboard/low-vision user:** a visually clipped commit scope is harder to verify; compact toolbars mean many focus stops. Source supplies accessible labels, visible focus and dialog trapping, but a complete keyboard-only commit flow, screen reader output, 200% zoom and quantitative contrast were not audited. No claim of an observed unlabeled control or contrast failure.
- **Jordan, first-time Git user:** staging hint gives a useful first action. “Sign-off” versus “Sign,” HEAD and unversioned vocabulary still ask for prior Git knowledge. This is not a reason to remove domain language, but a reason to explain the few choices with irreversible implications at their point of use.
